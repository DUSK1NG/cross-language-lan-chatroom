# 私聊功能设计说明

## 1. 目标

在现有群聊、用户代码和长度头 + JSON 协议基础上，增加点对点私聊。用户通过唯一代码定位目标用户，服务端负责查找目标并转发消息；私聊不会进入群聊广播。

命令格式：

```text
/msg Bob#BOB01 你好
```

用户名可以重复，代码不区分大小写且必须唯一。因此 `BOB01`、`bob01` 和 `Bob01` 指向同一个在线身份。

## 2. 协议

客户端发送：

```json
{
  "type": "private_chat",
  "target_user_code": "BOB01",
  "content": "你好"
}
```

服务端成功后只发送给发送者和目标用户：

```json
{
  "type": "private_chat",
  "username": "Alice",
  "user_code": "A001",
  "target_user_code": "BOB01",
  "content": "你好"
}
```

发送者身份由当前 TCP 连接绑定，服务端不会信任客户端提交的 `username` 或 `user_code`。`target_user_code` 由客户端提供，但必须经过服务端规范化、合法性检查和在线用户查找。

失败时只通知发送者：

```json
{
  "type": "error",
  "content": "Target user not found"
}
```

第一版规则：目标必须在线；不能给自己发消息；目标代码不存在或格式非法时不转发；私聊内容沿用群聊的 UTF-8 和 64 KiB 限制；不保存离线消息。

## 3. 服务端路由

`Hub` 继续作为 `ActiveCodes` 的唯一拥有者。客户端读协程只负责解析数据并向 Hub 发送私聊请求，不直接读取或修改共享 map。

建议新增私聊请求事件：

```go
type PrivateMessageRequest struct {
    Sender     *Client
    TargetCode string
    Content    string
}
```

Hub 收到事件后按以下顺序处理：

1. 规范化目标代码。
2. 在 `ActiveCodes` 中查找目标连接。
3. 未找到时只向发送者投递错误。
4. 发送者和目标不是同一连接时，构造服务端确认过身份的 `private_chat` 消息。
5. 分别投递给发送者和目标，不经过 `Broadcast`，因此第三个客户端不会看到私聊。

所有写 socket 的操作仍由对应客户端的 writer goroutine 执行。

## 4. C++ 客户端行为

客户端命令解析器从 `/msg ` 后读取目标身份和消息正文，要求目标身份包含 `#`，并提取 `#` 后的代码作为 `target_user_code`。客户端只做基本格式检查，最终合法性由服务端决定。

收到 `private_chat` 后：

- 发送者显示：`[Private -> Bob#BOB01] 你好`
- 接收者显示：`[Private from Alice#A001] 你好`

显示方向通过比较当前登录身份与服务端返回的发送者身份判断；代码比较使用不区分大小写规则。

## 5. 错误处理

- `/msg` 缺少目标或正文：客户端本地提示命令格式。
- 目标代码不存在：服务端只向发送者返回错误。
- 目标代码指向自己：服务端只向发送者返回错误。
- 内容为空、过长或 JSON 字段类型不正确：按现有协议校验流程返回错误，不崩溃。
- 客户端伪造发送者字段：服务端覆盖为连接绑定身份。
- 目标断线：Hub 的注销流程移除代码映射；正在处理的私聊失败时不影响服务器和其他连接。

## 6. 非目标

本功能不增加账号密码、离线存储、消息撤回、已读回执、文件传输、加密或 GUI。
