# Stage 8：异常处理与稳定性设计

## 1. 目标

Stage 8 只加固现有聊天室的异常处理和资源生命周期，不新增账号、私聊、文件传输、TLS 或 GUI 等业务功能。

本阶段要保证：

- 非法 TCP 数据不会导致 Go 服务端崩溃；
- 半包、截断包、超长包和非法 JSON 会被安全拒绝；
- 客户端强制退出后，服务端能清理连接并继续服务其他客户端；
- 服务端突然关闭时，C++ 客户端能检测断开并安全退出；
- Go 的 channel、goroutine、socket 和 C++ 的 thread、socket 都能正确结束；
- 异常场景有可重复的自动化测试或本机集成测试。

## 2. 不在本阶段实现的内容

- 自动重连；
- TLS；
- 用户认证和密码；
- 文件、图片、音视频传输；
- 数据库；
- GUI；
- 新的聊天室业务命令。

## 3. 协议边界

当前协议仍使用：

```text
4-byte unsigned length header in network byte order
        +
UTF-8 JSON payload
```

最大 JSON payload 为 64 KiB。长度字段表示 payload 的字节数，不表示字符数。

服务端和客户端都必须在分配内存或解析 JSON 前验证长度，不能根据远端提供的异常长度直接申请内存。

## 4. Go 服务端异常策略

### 4.1 帧读取异常

Go 的帧读取函数遇到以下情况时返回错误：

- 长度头不足 4 字节；
- 长度为 0；
- 长度超过 64 KiB；
- payload 实际长度小于声明长度；
- 对端 EOF；
- connection reset 或其他 socket 读取错误。

payload 读取完成后，先检查 UTF-8 是否有效，再交给 `encoding/json` 解析。

### 4.2 消息解析异常

以下情况视为当前消息或连接非法：

- JSON 格式错误；
- 缺少 `type` 字段；
- 字段类型错误；
- `users` 不是字符串数组；
- 未知或不允许的消息类型；
- chat 内容为空或超过当前限制。

协议级错误连接采用连接终止策略：服务端尽力发送通用错误，然后结束当前连接，避免继续使用状态不可信的连接。

### 4.3 连接生命周期

- 登录前出错时，服务端尽力返回 `error` 或 `login_error`，随后关闭连接；
- 登录成功后发生 EOF、连接重置或非法包时，read goroutine 结束并请求 Hub 注销；
- write goroutine 发送失败时，也请求 Hub 注销；
- Hub 是 `Clients`、`Send` channel 和在线代码集合的唯一所有者；
- `Send` channel 只由 Hub 关闭，其他 goroutine 不直接关闭或写入它；
- 注销操作必须能安全处理重复请求；
- 清理连接后广播离线消息，但清理失败不能影响其他客户端。

不把 `recover` 作为主要修复手段。优先通过 channel 所有权、注销顺序和状态检查避免 panic。

## 5. C++ 客户端异常策略

### 5.1 建立连接

- `WSAStartup` 失败：显示错误并退出；
- `socket` 失败：显示错误并清理 Winsock；
- `connect` 失败：显示错误、关闭 socket 并调用 `WSACleanup`。

### 5.2 发送和接收

- `send_all` 失败：停止客户端运行；
- `recv_all` 遇到 `recv == 0` 或 `SOCKET_ERROR`：报告连接丢失；
- 长度为 0 或超过 64 KiB：拒绝接收；
- JSON 解析失败或字段类型错误：报告协议错误并停止通信；
- 不自动重连，先保证一次连接的退出路径正确。

推荐的退出顺序：

```text
设置 running = false
        ↓
shutdown(socket, SD_BOTH)
        ↓
等待接收线程 join
        ↓
closesocket(socket)
        ↓
WSACleanup()
```

socket 的关闭责任必须集中，避免主线程和接收线程重复关闭同一个 socket。

## 6. 测试策略

### 6.1 Go 协议测试

使用内存缓冲区或 `net.Pipe` 覆盖：

1. 不足 4 字节的长度头；
2. 长度为 0；
3. 长度超过 64 KiB；
4. 声明长度大于实际 payload；
5. 非法 UTF-8；
6. 非法 JSON；
7. 缺少 `type`；
8. `users` 非数组；
9. `users` 数组元素非字符串。

### 6.2 Go 连接和 Hub 测试

- 客户端在登录前强制断开；
- 客户端在登录后强制断开；
- 客户端发送非法包后连接终止；
- 连接注销后，Hub 仍能接受新客户端；
- 重复注销不会 panic；
- write 失败不会让 Hub 或 Server 进程崩溃；
- Hub 的 outbound 事件晚到时不会写入已注销客户端；
- 服务端在异常客户端退出后仍可广播给正常客户端。

### 6.3 C++ 验证

- 使用 C++17、警告选项和 Winsock2 编译；
- 测试连接失败、服务端关闭、服务端主动断开；
- 验证接收线程能结束，主线程能 join；
- 验证无未处理异常、无未关闭的客户端进程；
- 如需构造非法数据，使用受控测试程序或 Go 测试辅助代码，不修改正式协议行为。

### 6.4 本机和局域网验收

所有异常测试按以下顺序执行：

1. localhost 单客户端；
2. localhost 双客户端；
3. 两台电脑局域网；
4. Ethernet 服务端 + Wi-Fi 客户端。

网络介质不是协议异常的根因。若局域网测试失败，单独检查 IP、端口、防火墙、AP Isolation、VLAN 和路由互通。

## 7. 测试矩阵

| 场景 | 预期结果 |
|---|---|
| 客户端连接不存在的端口 | C++ 显示连接失败并退出 |
| 客户端强制关闭 | Go 注销该客户端并继续运行 |
| 服务端突然关闭 | C++ 显示连接丢失并安全退出 |
| 长度头不完整 | Go/C++ 拒绝该帧，不崩溃 |
| 长度为 0 | 拒绝该帧 |
| 长度超过 64 KiB | 拒绝该帧 |
| payload 截断 | 连接结束，不等待无限数据 |
| 非法 UTF-8 | 拒绝消息或关闭协议连接 |
| 非法 JSON | 拒绝消息或关闭协议连接 |
| 字段类型错误 | 拒绝消息或关闭协议连接 |
| 重复注销 | 无 panic、无重复资源释放 |
| 异常客户端之后连接新客户端 | 新客户端正常登录和聊天 |

## 8. 完成标准

Stage 8 完成必须满足：

- `go test ./...` 通过；
- `go test -race ./...` 通过；
- `go vet ./...` 通过；
- C++ C++17 警告编译通过；
- 协议异常测试全部通过；
- 服务端突然关闭、客户端强制退出测试通过；
- 测试后没有残留服务端、客户端进程或 8888 端口监听；
- 工作区没有未记录的临时文件；
- README 或 Stage 8 文档记录异常处理限制和测试方式。

## 9. 已知取舍

- 第一版不自动重连，用户需要重新启动客户端；
- 为防止内存和资源耗尽，超长或异常帧会导致当前连接终止；
- 慢客户端可能被服务端移除，后续版本再设计更细致的背压策略；
- Windows 控制台输入和输出同时发生时，提示文字可能与正在输入的文本交错，这不影响协议安全性。
