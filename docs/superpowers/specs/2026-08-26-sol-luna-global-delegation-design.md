# Sol–Luna 全局委派模式设计

**日期：** 2026-08-26  
**状态：** 已批准，等待实施计划

## 背景

用户希望在主对话选择 Sol Max 时，由 Sol 负责需求理解、架构决策、计划、任务拆分、监督和最终验收；由固定为 `gpt-5.6-luna`、推理强度 `max` 的 `luna_worker` 自动承担边界明确的实现、编辑、测试、构建和信息收集任务。

现有个人代理文件位于 `~/.codex/agents/luna-worker.toml`，已正确声明 `name`、`description`、`model`、`model_reasoning_effort` 和 `developer_instructions`。现有全局 `~/.codex/AGENTS.md` 只规定中文输出和简洁表达，`~/.codex/config.toml` 尚无 `[agents]` 配置。

## 目标

- 对所有 Codex 项目启用“Sol 主导、Luna 执行”的平衡委派模式。
- 让主代理优先识别适合 Luna 的受限任务，无需用户逐次确认。
- 保留 Sol 对歧义、架构、安全、跨模块决策和最终完成声明的所有权。
- 通过任务契约、写入并发限制和双层验收降低越界修改与错误完成声明的风险。
- 保留项目级 `AGENTS.md` 覆盖全局策略的能力。

## 非目标

- 不把所有工具调用机械地切换给 Luna。
- 不让 Luna 自行决定产品范围、架构、安全策略或跨模块重构。
- 不自动提交、推送、发布、删除数据、安装大型依赖或执行其他外部副作用。
- 不为内置代理或未来自定义代理统一指定 Luna 模型。
- 不同时运行会修改相同文件或共享状态的多个写入代理。

## 总体架构

```text
用户请求
  -> Sol：理解、澄清、决策和任务拆分
  -> Sol：判断任务是否满足委派条件
     -> 否：Sol 直接处理或向用户请求决策
     -> 是：用受限契约启动 luna_worker
  -> Luna：检查相关上下文、执行、针对性验证
  -> Luna：返回 Outcome / Changes / Validation / Risks
  -> Sol：检查状态、关键差异、范围和验证证据
  -> Sol：必要时补跑高层验证
  -> Sol：整合并向用户交付最终结果
```

委派以完整子任务为单位，不在同一个代理线程内按“思考”和“工具操作”切换模型。未委派的分析、编辑和命令仍由主线程 Sol 执行。

## 三层配置

### 1. 全局 `~/.codex/AGENTS.md`

保留现有中文输出和简洁表达规则，追加 `Sol–Luna 协作策略`。该策略应：

- 要求主代理在实现工作开始前判断是否存在可独立验收的受限子任务。
- 对符合条件的任务优先使用 `luna_worker`，无需每次向用户确认。
- 明确 Sol 和 Luna 的职责、禁止委派范围、委派契约和双层验收。
- 默认只允许一个写入型 Luna；只读检查或互不依赖的测试才允许并行。
- 明确项目级规则可以收窄、关闭或覆盖全局委派策略。
- 允许在任务极小、委派开销高于执行成本时由 Sol 直接完成。

### 2. `~/.codex/agents/luna-worker.toml`

保留以下模型配置：

```toml
model = "gpt-5.6-luna"
model_reasoning_effort = "max"
```

强化代理说明和执行契约：

- 开始前识别目标、输入、文件或模块所有权、约束、验收标准和验证目标。
- 修改前检查相关文件及已有工作区变更，保留用户和其他代理的修改。
- 只修改被明确授权的文件或职责范围。
- 遇到实质歧义、所有权冲突、权限阻塞或必须扩大范围时停止并返回 Sol。
- 不继续委派，不自行提交、推送、发布或执行破坏性和外部副作用操作。
- 使用用户当前语言回复；默认交接格式为 `Outcome / Changes / Validation / Risks`。
- 不设置固定 `sandbox_mode`，继承主任务当前选择的权限模式。

### 3. `~/.codex/config.toml`

新增：

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 3
```

不设置 `default_subagent_model` 或 `default_subagent_reasoning_effort`。`luna_worker` 由自己的代理文件固定模型；其他代理继续按显式启动值、全局默认或父代理设置解析。

## 路由规则

只有同时满足以下条件时才自动委派：

1. 目标和交付物可以明确描述。
2. 文件、模块或只读调查范围可以划定。
3. 不需要 Luna 自行作产品、架构或安全决策。
4. 操作可恢复且没有未授权的外部副作用。
5. 存在针对性的验证方法。

适合 Luna 的任务包括：

- 单一模块或明确文件集合内的功能实现与缺陷修复。
- 测试编写、测试运行、构建和静态检查。
- 配置、文档和机械性转换。
- 范围明确的代码路径调查、日志分析和信息收集。

保留给 Sol 的任务包括：

- 需求仍有实质歧义的工作。
- 架构、产品范围、安全策略和跨模块取舍。
- 高风险或难以恢复的操作。
- 任务拆分、子代理协调、结果整合和最终完成声明。
- Luna 失败、超时、越界或返回阻塞后的处置。

## 委派契约

每个 Luna 任务必须包含：

```text
Objective: 要完成什么
Ownership: 允许检查和修改哪些文件或模块
Context: 必要背景与需要保留的已有变更
Constraints: 禁止事项和必须保持的行为
Acceptance: 可验证的完成条件
Validation: 应运行的检查或测试
Return: Outcome / Changes / Validation / Risks
```

没有足够信息填写该契约时，Sol 不应启动写入型 Luna。

## 并发与共享工作区

- 默认最多一个写入型 Luna 处于活动状态。
- 只读调查、互不依赖的测试或无共享输出的任务可以并行。
- 并行任务必须有互斥的文件所有权或明确的只读职责。
- Luna 不得回滚或覆盖用户、Sol 或其他代理的已有修改。
- 用户中途改变要求时，由 Sol 统一停止、调整或重新委派任务。

## 异常处理

- **歧义或范围扩大：** Luna 停止修改，返回阻塞原因和最小决策请求。
- **测试失败：** Luna 返回原始失败与已确认的影响，不得使用推测性通过结论。
- **越界修改：** Sol 拒绝接收结果，检查工作区并决定重新委派或自行修正。
- **超时或不可用：** Sol 根据任务规模自行完成或向用户说明限制，不无限重试。
- **权限或外部副作用：** 沿用主任务权限与审批；未经授权不得绕过审批。
- **用户转向：** Sol 停止旧任务，防止 Luna 继续执行过时目标。

## 双层验收

### Luna 自验

- 运行与改动最相关、范围最窄的测试或检查。
- 检查实际修改范围与被委派所有权一致。
- 返回命令、退出状态、测试数量或失败证据。

### Sol 复核

- 检查工作区状态、关键差异和未预期文件。
- 核对验收标准与 Luna 的验证证据。
- 对跨模块、安全、发布或高风险修改补跑更高层验证。
- 仅在当前证据支持时向用户声明完成。

## 验证与启用

实施后执行以下检查：

1. 验证 `luna-worker.toml` 与 `config.toml` 的 TOML 语法和必需字段。
2. 确认原有全局中文及简洁输出规则未被覆盖。
3. 确认没有配置全局默认 Luna 模型。
4. 确认 `[agents]` 已启用且并发上限为 3。
5. 新建 Codex 任务，要求说明当前协作规则，确认全局 `AGENTS.md` 已加载。
6. 在新任务中提交一个边界明确的小型修改，确认使用 `luna_worker`、返回结构化交接，并由 Sol 完成复核。
7. 提交一个含架构歧义的请求，确认 Sol 不会直接把决策交给 Luna。

Codex 在任务启动时构建指令链，因此文件写入后的动态加载验证必须在新任务中完成。
