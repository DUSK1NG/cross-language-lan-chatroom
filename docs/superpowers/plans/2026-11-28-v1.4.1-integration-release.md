# LAN Chat 1.4.1 Integration and Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将四组安全修复按顺序集成到当前 1.4.1 版本线，经候选分支评审后合并 `master`，发布 `v1.4.1`，完成生产验证与回滚准备。

**Architecture:** 使用 `stage/1.4.1-security` 候选分支逐计划实施和提交；每个计划独立通过测试后再进入下一个；PR 合并后保持版本 1.4.1，创建 annotated tag 触发既有 Release 工作流；发布前验证全部签名资产，发布后执行备份、部署、健康和聊天/附件冒烟。

**Tech Stack:** Git、GitHub CLI、GitHub Actions、PowerShell、Cargo、pnpm、Gradle、SQLite、systemd。

**Spec:** `docs/superpowers/specs/2026-11-28-lan-chat-security-remediation-design.md`

## Global Constraints

- 当前 `master` 和所有版本元数据保持 `1.4.1`；`v1.4.1` 标签当前不存在，不得升到 1.4.2。
- 实施顺序固定：服务端 P0 → 配额与客户端 → 发布链 → 运维与恢复 → 本计划。
- 不得提交未跟踪的 `CON`、`.tools/`、`out/`、`release/`、数据库、证书、私钥、日志或本机缓存。
- 所有外部写操作必须先展示具体命令和影响；用户已授权范围包括 GitHub 治理、公开历史清理和生产发布，但破坏性历史重写、强推和凭据轮换仍需在执行前复核确认。
- Release 资产必须由发布链计划生成的签名和验签脚本通过检查；未签名 ZIP 或校验清单不得发布。
- 生产数据库迁移前必须完成 `lan-chat-backup backup` 和 `verify`；失败时停止发布并恢复迁移前快照。
- 不执行破坏性降迁移；旧二进制只能用于迁移前备份恢复。
