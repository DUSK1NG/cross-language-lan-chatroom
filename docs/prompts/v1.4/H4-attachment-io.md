# H4 执行版：LAN 附件 IO 移出 Hub 锁

本阶段可延期。纳入 v1.4 时，H3 须已通过。现有 S0 端到端附件收发回归继续作为基础。目标是大文件传输期间，其他用户可以正常聊天，文件与权限状态可恢复。

## 开工决策

- **H4 SQLite。**先确认当前写连接、busy timeout、读写竞争和本地文件系统。在代表性负载下验证短写事务。若须启用 WAL，限定到实际需要的数据库，并走已有授权门。明确备份、恢复、checkpoint 和打包排除。竞争测试仍要验证写入，因为 WAL 允许读写并行，写事务仍逐个执行。
- **H5 文件发布。**确认文件就绪、数据库可读和权限生效的顺序，以及各中断位置的恢复行为。通过决策和测试设计后再改写路径。保留可恢复的上传状态，正式文件可靠落盘后再标记可读。涉及权限变化的处理见下文。

## 实施要求

1. **划分工作。**使用有界队列与专用 worker。将解码、摘要、文件写入、下载读取及清理移出全局 Hub 锁，数据库写事务只处理必需状态。worker 保持同一传输的命令顺序，响应继续带原 `command_id`。定义队列满、连接中断、重启和上传过期时的可见结果。
2. **一致性。**请求快照关联连接 ID、用户、房间代次与所需权限。明确权限变更与附件发布的共同排序点，在发布和回包前校验授权。被踢、退房、同码重连、同名房间删后重建时，旧任务无法发布或回包给新会话。按旧实现核对 init、chunk、resume、commit、download 的身份、房间、作者、期限、配额与错误文本。
3. **可恢复提交。**写入和校验暂存文件，记录发布所需的中间状态，同卷移入正式路径后再事务性发布元数据并收尾上传。标记可读前保留必要的恢复记录。处理 rename、数据库提交或进程中断，重启可识别并完成发布或恢复到可重试状态。把配额和清理放在对应状态推进里，避免半成品可见或一次失败导致上传不可恢复。
4. **并发与性能。**优先复用 H1 的 `test-hooks`，只在测试构建中阻塞附件 worker，确认另一连接在约定时限内完成聊天。覆盖单块失败、权限变化、并行写入及中断恢复。用同一 100 MiB 文件、相同环境对照上传期间聊天延迟，分别记录并行与串行行为。
5. **结构验收。**检查 LAN 附件分派及锁范围，确认附件文件 IO 和长事务已移出 Hub 锁。其余证书和启动文件 IO 按原职责保留。把权限与错误对照、恢复结果及性能记录放进本阶段报告，更新现有架构与测试文档。
