# S2 执行版：局域网房间与权限持久化

H2 通过后执行。延续现有局域网房间与审批体验。先读 `server-rust/src/lan/{mod,store,rooms,messages}.rs`、`docs/administrator.md` 与 `server-rust/tests/lan_desktop.rs`。

## 实施要求

1. **复用现有房间数据。**当前通过 `protected_rooms` 保存带密码的房间、房主和白名单，启动时已经加载。LAN 库迁移到 `user_version=2`，复用或在事务内迁移该数据，补齐普通房、无密码私密房以及所需权限。保留 bcrypt 密码、房主和已有白名单，`lobby` 继续按虚拟房间处理。沿用 UUID 区分房间代次，同名删房重建获得新代次。
2. **明确权限范围。**房主保有现有全局权限。任命的房间管理员仅管理指定房间的成员与房间内容，连接审批仍归房主。现有禁言沿用原生效范围，由房主操作并按用户身份持久化。客户端按权限显示对应操作，旧客户端不能借新角色获得全局权限。
3. **写入与恢复。**房间和权限变更由 DB 事务先提交，再发布对应内存状态和响应。失败时保留旧状态并反馈。成员移除、删房和同名重建一起验证历史、离线消息及附件权限，避免旧的访问规则复用到新房间。
4. **逐次连接审批。**房间白名单只决定审批完成后的房间访问。保留房主本机开房的既有登录路径。访客重连沿用真实审批状态，客户端显示「等待房主批准」，明确拒绝和超时结果。房主可辨认重连申请的条件须来自服务端可验证的状态，缺少依据时按普通申请显示。
5. **文档。**在现有管理员和架构文档说明持久化范围、权限与连接审批的区别。覆盖批准前、批准后以及离房后的权限变化。

## 验收

```powershell
cargo test --locked -p lan-chat-server
cargo clippy --locked -p lan-chat-server --all-targets -- -D warnings
```

用数据库副本先验证已有密码房迁移，再完成「建普通房及私密房 → 设置成员与角色 → 禁言 → 重启 → 访客再次申请 → 审批后进入」。确认白名单成员与房主权限、密码与禁言都按原定义生效，并验证数据库写失败和删房重建不会产生权限残留。记录迁移前后版本、双端结果与旧数据验证。
